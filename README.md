# 如何让代码变得绝对安全

> 一份不打算安慰你的安全实践清单。

## 0. 先说清楚一件事

**不存在“绝对安全”的代码。**

安全不是“没有任何东西可被利用”，而是在明确的威胁模型下，把风险压到可接受、可度量、可追溯的范围内。

一个空仓库看起来零风险，但风险不会消失，它只是换了地方：仓库权限、协作者、CI 里的 token、依赖链、以及维护者的判断力。把“不写东西”当成安全策略，等于把风险从代码搬到了你根本没在看的地方。

## 1. 先把威胁模型写下来

不用写成长篇报告，三句话就够：

- **资产**：这个系统里什么东西值钱？（用户数据、支付能力、内网入口、发布权限）
- **攻击者**：谁会想要它？（外部扫荡的自动化、有账号的内部人、供应链上的第三方）
- **入口**：他们能从哪儿进来？（公网接口、依赖包、CI 流水线、人的邮箱）

没有威胁模型的“安全加固”只是在堆配置，你不知道哪些有用，也不知道哪些该省。

## 2. 密钥永远不进仓库

- `.gitignore` 在第一次提交前就写，不是出事后再补。
- 本地加 pre-commit 钩子（gitleaks / trufflehog），让泄露在提交前就被拦下。
- 打开 GitHub 的 secret scanning 与 push protection，当作第二道网。
- 代码里不做“没配环境变量就用默认值”的降级，默认值就是把生产密钥写进源码的委婉说法。
- **一旦泄露，第一动作是轮换（rotate），不是删掉那次提交。** 历史还在，fork 还在，CI 缓存还在，别人的终端里也还在。

## 3. 权限按最小化给

- token 只给需要的 scope，只给需要的时间。
- 工作流里显式声明 `permissions: read-all` 起步，需要写权限的 job 单独开口子。
- 生产环境的读写账号分开，能读的不能写，能写的不能建表。
- 不要拿个人长期 token 跑自动化，那是一把不会过期的钥匙。

## 4. 所有输入都是敌意的

- 校验放在服务端。前端的校验是给用户看的体验，不是安全边界。
- 查询用参数化，不拼字符串；拼 SQL 的地方就是注入的地方。
- 输出按上下文编码，HTML、URL、JS、Shell 各有各的转义规则。
- 文件上传要管三件事：类型、大小、路径。路径穿越比想象中常见。
- 服务端发起的请求要做出网白名单，否则 SSRF 会把你的内网当代理用。

## 5. 依赖是别人写的代码

- 锁文件进仓库，版本固定，升级是一次有意识的动作而不是偶然结果。
- GitHub Actions 固定到 commit SHA，不用 `@main`，也不用浮动 tag。
- 定期跑依赖审计和 Dependabot，但要清楚：审计通过只说明“没有已知问题”，不等于安全。
- 维护一份 SBOM。出事时能在五分钟内说清你到底用了什么，比事后翻 lock 文件值钱得多。

## 6. 默认拒绝

- 用白名单，不用黑名单。黑名单永远漏一项，白名单漏的那项是“不能用”。
- 失败要关闭（fail closed），不要失败就放行（fail open）。鉴权服务挂了，应该是拒绝服务，不是全员通过。
- 隐藏按钮不是权限。前端藏起来的东西，后端必须再判一次。

## 7. 让机器守门，别靠记性

CI 至少四道闸：lint → 单元测试 → 静态分析（SAST）→ 依赖与密钥扫描。

分支保护要开：必须评审、必须绿灯、禁 force push、禁直接推主干。

发布要有签名、可追溯的构建记录、以及明确写好的回滚步骤。不能回滚的上线不叫上线，叫赌博。

## 8. 能看见，才管得住

- 日志里不写密码、token、完整证件号；日志本身也是泄露源。
- 敏感操作留审计：谁、什么时候、改了什么。
- 告警要发到有人真的会看的地方。发进一个没人订阅的邮箱，等于没有监控。

## 9. 出事之后

提前想好三件事：谁能停服务、谁能轮换密钥、谁对外说话。演练一次，比写十页预案有用。

复盘写在文档里，写清楚“什么失效了、哪道检测本该拦住它”，不追究个人。追究个人只会让人下次瞒着你。

## 10. 诚实的结论

上面每一条都做完，你得到的是“风险已知、可控、可追溯”。这已经是很高的标准，但它仍然不是“绝对安全”。

任何声称自己绝对安全的方案，通常只是把风险藏在了你没检查的地方。
